# PR 컨벤션

## PR 제목

```
type: 한 줄 요약
```

## PR Type

아래 중 **하나만** 선택해 체크박스에 `[x]` 표시한다.

| Type       | 사용 시점                                              |
| ---------- | ------------------------------------------------------ |
| `feat`     | 기능 구현 (새로운 요구사항 구현, 기존 기능 개선)       |
| `fix`      | 버그 수정                                              |
| `refactor` | 코드 리팩토링 (성능 개선, 구조 변경, 기능 수정 없음)   |
| `style`    | 포매팅, 린트 (기능 변화 없음)                          |
| `chore`    | 환경설정, 패키지 관리, 라이브러리 설치 등              |
| `docs`     | 문서 작성                                              |

## 버전 레이블

v3 머지 1건이 릴리즈 1건이다. PR 에 붙인 레이블로 `version-bump` 체크가 `package.json` 버전을 올린다. 셋 중 **하나만** 붙이고, 해당 없으면 붙이지 않는다.

| 레이블  | 붙이는 경우                                                   | 흔한 PR Type               |
| ------- | ------------------------------------------------------------- | -------------------------- |
| `major` | 블로그 구조나 스택 개편 (v2 → v3 같은 에픽 단위)              | -                          |
| `minor` | 방문자가 쓸 수 있는 기능이 새로 생긴다                        | `feat`                     |
| `patch` | 운영에 나가는 코드가 바뀐다. 버그 수정, 화면 스타일, 리팩토링 | `fix`, `style`, `refactor` |
| 없음    | 운영 화면과 관계없다. 문서, 스킬, CI, 개발 설정               | `docs`, `chore`            |

- PR Type 은 출발점일 뿐이다. `chore` 라도 운영 번들에 들어가는 의존성 업데이트면 `patch` 다
- 버전 레이블이 둘 이상이면 체크가 실패한다

## Base 브랜치

고정값으로 적지 않는다. 레포의 기본 브랜치를 조회해서 쓴다.

```bash
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
```

## 이슈 번호 추출

브랜치명에서 자동으로 추출한다.

```
feat/#1   → closes #1
fix/#2    → closes #2
```

패턴이 `{prefix}/#{number}` 형식이 아니면 이슈 번호 없이 PR을 생성한다.

## 본문 형식

```markdown
## Pull Request Type

- [ ] feat: 기능 구현 (새로운 요구사항 구현, 기존 기능 개선)
- [ ] fix: 버그 수정
- [ ] refactor: 코드 리팩토링
  > 성능 개선, 구조 변경, 기능 수정 없을 때
- [ ] style: 포매팅, 린트 (기능 변화 없음)
- [ ] chore: 환경설정, 패키지 관리, 라이브러리 설치 등
- [ ] docs: 문서 작성

## 관련 이슈

closes #{이슈번호}

## 작업 내용

### {작업 단위 제목}

- {무엇이 바뀌었는지}
- {왜 바꿨는지, 이제 어떻게 동작하는지}

### {작업 단위 제목}

- {...}

## 검증

- {확인한 것과 결과}
```

## 작업 내용 작성 기준

「작업 내용」 절은 **그대로 릴리즈 노트가 된다.** 버전 레이블이 붙은 PR 이 머지되면 `release` 워크플로가 이 절을 옮겨 발행한다 (`.github/scripts/buildReleaseNotes.ts`).

- 독자는 블로그를 보는 사람이다. 파일과 함수 이름 대신 달라진 동작을 적는다. 코드 이름은 꼭 필요할 때만 백틱으로 쓴다
- 커밋 이력(`git log --oneline main..HEAD`)을 **의미 있는 작업 단위로 묶어** 소제목(`### 제목`)을 나눈다. 번호는 붙이지 않는다
- 소제목 아래는 `- 문장` 목록으로, `~습니다` 체로 쓴다. 단위마다 **무엇이** 바뀌었고 **왜** 바꿨는지 적는다
- 설계 결정이 있으면 그 이유를 함께 적는다 (대안 대비 선택 근거, 해결한 문제 등)
- 테스트 결과, 로컬 확인, 머지 뒤 할 일은 「작업 내용」이 아니라 `## 검증` 같은 별도 절에 둔다. 다음 `## ` 제목에서 노트가 끊긴다
- 릴리즈 노트의 섹션은 PR 제목 타입으로 정해진다: `feat` → Feature, `fix` → Fix, 나머지 → Etc
