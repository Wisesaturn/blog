# PR 컨벤션

## PR 제목

```
type: 한 줄 요약
```

## PR Type

아래 중 **하나만** 선택해 체크박스에 `[x]` 표시한다.

| Type       | 사용 시점                                              |
| ---------- | ------------------------------------------------------ |
| `feat`     | 기능 구현 (새로운 요구사항 구현, 기존 기능 개선)       |
| `fix`      | 버그 수정                                              |
| `refactor` | 코드 리팩토링 (성능 개선, 구조 변경, 기능 수정 없음)   |
| `style`    | 포매팅, 린트 (기능 변화 없음)                          |
| `chore`    | 환경설정, 패키지 관리, 라이브러리 설치 등              |
| `docs`     | 문서 작성                                              |

## Base 브랜치

항상 `main`을 사용한다.

## 이슈 번호 추출

브랜치명에서 자동으로 추출한다.

```
feat/#1   → closes #1
fix/#2    → closes #2
```

패턴이 `{prefix}/#{number}` 형식이 아니면 이슈 번호 없이 PR을 생성한다.

## 본문 형식

```markdown
## Pull Request Type

- [ ] feat: 기능 구현 (새로운 요구사항 구현, 기존 기능 개선)
- [ ] fix: 버그 수정
- [ ] refactor: 코드 리팩토링
  > 성능 개선, 구조 변경, 기능 수정 없을 때
- [ ] style: 포매팅, 린트 (기능 변화 없음)
- [ ] chore: 환경설정, 패키지 관리, 라이브러리 설치 등
- [ ] docs: 문서 작성

## 관련 이슈

closes #{이슈번호}

## 작업 내용

### 1. {작업 단위 제목}

{이 작업이 왜 필요했는지, 무엇을 해결했는지 2~4문장으로 서술}

### 2. {작업 단위 제목}

{...}
```

## 작업 내용 작성 기준

커밋 이력(`git log --oneline main..HEAD`)을 기반으로 **의미 있는 작업 단위로 묶어** 서술한다.

- 파일 목록 나열 ❌ — "A.ts 수정, B.ts 신설" 같은 기계적 나열은 하지 않는다
- 작업 단위로 소제목(`### n. 제목`)을 나눠 각 단위가 **왜** 필요했고 **무엇을** 해결했는지 설명한다
- 설계 결정이 있으면 그 이유를 함께 서술한다 (대안 대비 선택 근거, 해결한 문제 등)
